# 景点图文、可讨论的行程草案与预算

首次整体规划顺序：开场短段 → 代表景点 → 简版行程草案 → 预算参考 → 小结和自然追问。短途至少3个景点，5天及以上至少5个（通常5～6个），手机最多支持8个。短途目标1000～1500字、长途1600～2200字，最多2600字；生成输出上限6144 tokens，原有单消息4000字符/对话32000字符/请求和每日限额保持不变。后续补充条件时仅修改相关内容，再逐步细化交通、餐食、休息及时间段。地图不在此功能范围内。

## 回复和显示约定

服务端 `TRAVEL_SYSTEM_INSTRUCTION` 约定独立的“景点推荐”“行程草案”“预算参考”“小结”标题。景点的完整日文原名（含必要中文括号）用成对双星号、独占一行，下一行是介绍；手机清理标记后保留全宽文字，在每个景点介绍下方、下一景点之前插入横图。保留既有文字字号、段落留白、行程和预算布局。图片不提供点击跳转；查不到图片时保留完整文字，不能拿其他景点冒充。

静冈缺图修复：日本平和热海温泉的百科封面是地图，候选筛选现已识别其条目中的 Nihondaira/Atami Onsen 实景文件名；同时排除广播塔和球场。“白糸ノ滝”匹配已核实的静冈具体瀑布条目；没有地区限定的“白糸の滝”仍不强配图片，避免跨县同名地点混淆。批量文件列表上限提高至500条，最多8个地点、每处6个候选（最多48个元数据文件），其余来源、许可和缓存规则保持不变。三处实际照片均已取得。

行程以 `Day 1：区域或路线` 分组，上午/下午/晚上各列重点，按用户实际天数生成；天数未知时明确示例假设。超过七天先覆盖整个旅程的阶段概要，再分段细化。草案可在同一对话中修改；本次没有新增单元格直接编辑、确认保存或购买功能。

预算先说明人数/每天或全程/包含和不包含的范围，随后用连续的 `项目｜估算金额` 行。手机将符合预算标签规则的两行以上内容渲染为项目/金额两列、细线分隔的表格；普通路线文字和 Markdown 分隔符不会误转预算表。所有数额为规划估算，未确认档次为建议。

保持以前的逐步展示、发送按钮始终为“发送”、本轮消息置顶后不自动追到底部、图片匹配及随机选择、日文名称保留、完整多轮上下文和原有云端额度机制。首次规划较完整，后续仅问住宿/预算或改某一天时不机械重发整篇。
